Cracking the Hash

A CyberChef field investigation into how — and why — your passwords never get stored as plain text.

Case briefing

When you type a password into a real login form, the site is not supposed to keep a copy of what you typed. Instead, it runs your password through a one-way math function called a hash, and stores only the scrambled result. Every time you log in again, the site re-hashes what you type and checks whether the two scrambled results match.

If hashing is one-way, how does anyone ever verify a password — and what happens when the hash itself gets stolen?

You'll answer that using CyberChef, a browser tool that lets you build a "recipe" of operations and watch data transform step by step. No installs, no accounts. Keep this page open in one tab and CyberChef in another.

Q5. MD5 and SHA1 are both considered "broken" for security purposes today, even though they still produce hashes here. Based on what you searched or already know, why might a shorter, older algorithm be considered weaker?

04

Salt in the recipe

Goal: see why sites add random "salt" before hashing.

  1. Set Input to: password and hash it with SHA256. Record the output.
  2. Now change Input to: passwordXyZ9 (imagine "XyZ9" is a random salt the site generated just for this account) and hash it with SHA256 again. Record the output.
Real systems store the salt alongside the hash, and generate a new random salt for every single account — even two people who both pick "password" end up with completely different stored hashes.

Q6. Two students in this class both used "password" as their (bad) password. Without salting, what would their stored hashes look like? With salting, what changes?

Q7. Attackers sometimes use pre-built lists of common passwords already matched to their hashes, called rainbow tables, to look up a stolen hash instantly. Why does salting make a rainbow table useless against these accounts?

05

Why length still wins

Goal: connect hashing to real password strength, without any hashing left to do.

Hashing protects a password once it's stored — but a weak password is still weak. If attackers get a stolen hash, they can't reverse it, but they can guess millions of candidate passwords per second, hash each guess, and check for a match. This is called a brute-force or dictionary attack. Roughly, here's how the search space grows:

Password styleExampleRough guesses needed to exhaust all options
4 lowercase lettersabcd~ 456,000
8 lowercase lettersabcdefgh~ 209 billion
8 mixed case + digitsaB3xQ9zK~ 218 trillion
12 mixed case + digits + symbolsTz9!kR2#vQmP~ 4.7 x 10^23

Q8. A common password ("password123", "qwerty", a name + birth year) can often be checked in seconds even after hashing, no matter how strong the algorithm is. Why doesn't a strong hash algorithm save a weak password?
